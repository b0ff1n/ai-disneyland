# Летопись учебных занятий

После **явного завершения урока** создать один файл `YYYY-MM-DD-<short-topic>.md` по [шаблону](../../templates/session-note.md). Один чат обычно соответствует одному уроку; несколько задач внутри него — наблюдения одного отчёта. Повторная просьба сохранить тот же урок не создаёт новый урок. Для разных уроков в один день использовать разные slug.

Это единственный журнал исторических событий. [Прогресс по предметам](../progress/) содержит текущие выводы, пробелы и следующие проверки со ссылками на отчёты. Не создавать параллельный CSV, реестр или базу данных. Не записывать настройку репозитория или добавление книги как обучение. Не восстанавливать прошедшие уроки из догадок.

## Формат версии 1

Каждый отчёт содержит ровно один блок с меткой `json`, без комментариев и завершающих запятых. JSON хранит наблюдения; остальной Markdown — открытые вопросы и следующий шаг. Имя файла без `.md` — устойчивый идентификатор записи; после сохранения его не менять. Шаблон и этот README не являются записями.

| Поле | Правило |
| --- | --- |
| `schema_version` | Число `1`. При будущей смене формата сохранить возможность чтения старой версии. |
| `record_type` | `session` для урока, `correction` для отдельного исправления исторической записи. |
| `date` | Реальная дата завершения урока в формате `YYYY-MM-DD`, совпадает с датой в имени файла. Если урок пересёк полночь, использовать дату завершения. Для исправления — дата исправления. |
| `timezone` | Часовой пояс IANA из контекста пользователя, например `Asia/Jerusalem`; если неизвестен — `null`. Не угадывать по часам машины. |
| `duration` | `null`, если пользователь не сообщил время; иначе объект, описанный ниже. |
| `observations` | Массив конкретных наблюдений; может быть пустым. Не добавлять вымышленные результаты ради заполнения шаблона. |

**Длительность необязательна.** Её отсутствие не мешает завершить и сохранить урок; не требовать ответа про время. Если пользователь сообщил длительность всего урока, записать `{"minutes": 45, "reported": "примерно 45 минут"}`. `reported` сохраняет его формулировку, в том числе приблизительность; `minutes` — число минут, только если оно однозначно следует из сообщения (допустима дробь). Для диапазона или неопределённого времени, например «30–40 минут», использовать `{"minutes": null, "reported": "30–40 минут"}`. Время только одной задачи можно сохранить в `evidence` этой задачи, не выдавая за время всего урока. Не вычислять длительность по переписке, числу сообщений или скорости решения. Не заменять неизвестное нулём.

## Наблюдения

Одна запись массива — одна конкретная попытка, действие или проверка. Повторная самостоятельная попытка после разбора может быть отдельным наблюдением; нельзя переименовывать первоначальное решение с подсказками в самостоятельное.

| Поле | Правило |
| --- | --- |
| `id` | Уникальное внутри отчёта значение `o1`, `o2`, …; после сохранения не перенумеровывать. |
| `subject` | Устойчивый код предмета; для существующих файлов прогресса — их имя без `.md`, например `calculus`, `linear-algebra`, `mechanics`. |
| `topics` | Непустой массив конкретных названий тем. При повторном обращении использовать прежнее название; не менять старые записи ради переименования. |
| `status` | Одно значение из словаря ниже; это вид работы, а не балл владения. |
| `result` | Что именно сделал ученик: шаг доказательства, решение, найденная ошибка или место остановки. Не ограничиваться «тема пройдена». |
| `assistance` | Кратко описать реально оказанную помощь: наводящий вопрос, конкретную подсказку, разбор готового решения. `none` — помощи не было, `unknown` — неизвестно. |
| `verification` | `verified` или `not_verified`. Проверка результата не означает владения всей темой. |
| `evidence` | Основание вывода: проверенные шаги текста/фото решения, ответ на проверочный вопрос или самоотчёт ученика. Указать границы проверки и неясности. |
| `sources` | Массив объектов `{"reference": "...", "locator": "..."}`; пустой массив, если источника нет. Правила ссылок ниже. |
| `corrects` | Обычно `[]`; в исправлении — ссылки на исправляемые наблюдения, например `learning/sessions/<имя-файла>.md#o1`. Это адрес записи и её JSON-id, а не Markdown-якорь. |

Словарь `status`:

- `read` — материал прочитан; само по себе не подтверждает понимания.
- `explanation_understood` — ученик сообщил о понимании или продемонстрировал его; различие отразить в `verification` и `evidence`.
- `attempted` — была попытка, но решение не завершено или содержит неустранённую ошибку.
- `solved_with_hints` — ученик завершил решение с подсказками; описать их в `assistance`.
- `solved_independently` — ученик завершил самостоятельную попытку; правильность отдельно отражается в `verification`.
- `solution_reviewed` — обсуждалось готовое решение; это не решение ученика.

Фраза «всё понятно» без проверки не даёт `verified`. Нечитаемое фото или неподтверждённое сообщение о самостоятельном решении оставляют результат `not_verified`. Если проверена только часть, выделить её в отдельное наблюдение либо оставить весь результат непроверенным и описать проверенную часть в `evidence`. Не выдумывать проценты, уровни или оценки владения.

## Источники и задачи

В `reference` хранить путь **от корня репозитория** или постоянный URL. Для учебника использовать `library/indexes/<book-id>.md`; в `locator` обязательно указать book ID/издание (либо точное описание перевода без выдуманного издания), главу/раздел, номер задачи или теоремы при наличии, печатную страницу и физическую PDF-страницу (счёт с 1). Номера и формулировку предварительно проверить по точному локальному PDF согласно [AGENTS.md](../../AGENTS.md). Индекс — навигация, а не доказательство содержания.

Для задачи без опубликованного источника сохранить её точное условие в `locator` или в обычном файле репозитория и сослаться на него. Для фото решения сохранить в `evidence` достаточно содержания проверенных шагов и замеченных ошибок: ссылка только на вложение в чате не переносима между машинами. Если точное условие или часть записи не удалось прочитать, прямо отметить это; не восстанавливать из памяти. Не использовать временные или абсолютные локальные пути.

## История и дальнейшее использование

После сохранения не переписывать старые наблюдения под нынешнюю оценку. Новая попытка — новое наблюдение в новом уроке. Если обнаружена ошибка в прежней записи, создать `YYYY-MM-DD-correction-<slug>.md` по тому же формату с `record_type: "correction"`, `duration: null` и непустым `corrects` у каждого исправления. В `result` и `evidence` описать исправление и его основание; исходную запись сохранить. Исправление не является новым уроком и не добавляет учебного времени.

При завершении урока:

1. Записать только фактические наблюдения, проверить дату, JSON, ссылки и отсутствие заполнителей.
2. При необходимости уточнить `learning/progress/<subject>.md`, сославшись на отчёт и id наблюдения; обновить краткий следующий шаг и ссылку на последний урок в `learning/now.md`. Не копировать всю историю в эти файлы.
3. Убедиться, что отчёт не игнорируется Git. Коммит и отправка — только по прямому запросу; до этого изменения ещё не перенесены на другие машины.

Для будущего графика, хронологии или карты читать датированные отчёты и их JSON-блоки: группировать по `date`, `subject`, `topics`, различать `status`, помощь и проверку, учитывать явные исправления через `corrects`. Считать уроки по уникальным файлам `session`, а не по количеству наблюдений; `correction`, README и шаблон исключать из числа уроков. Для времени использовать только сообщённые числовые значения и отдельно показывать, у скольких уроков длительность неизвестна или задана диапазоном. Число уроков, упоминаний темы и затраченное время не превращать в оценку владения. Старые записи без такого блока не дополнять задним числом догадками: показывать ограничения данных.

## Обзор пройденного за период

По просьбе «что мы прошли за год» или аналогичной собери понятную ретроспективу из отчётов за запрошенный период. Это карта фактически пройденного; `learning/roadmap.md` описывает планы и не служит доказательством выполненной работы.

- Покажи путь по предметам и темам: когда к ним обращались, какие книги и разделы изучали, какие теоретические вопросы обсуждали и какие задачи решали. В отчётах сохраняй и обсуждение теории, даже если задач не было; без проверки понимания отмечай `not_verified` и выбирай статус по реально выполненному действию.
- Различай знакомство с материалом, разбор объяснения, попытки, решения с помощью и проверенные самостоятельные решения. Несколько упражнений из главы не означают, что пройдена вся глава.
- Отметь изменения со временем, повторяющиеся трудности и оставшиеся пробелы. Обосновывай выводы ссылками на конкретные отчёты и id наблюдений; текущие файлы `progress/` используй как дополнение, сохраняя границы запрошенного периода.
- Учитывай доступные исправления к выбранным наблюдениям, даже если исправление сделано позже периода; явно отмечай такие позднейшие поправки. Сами исправления не считай занятиями.
- Кратко укажи охват и ограничения архива: число сохранённых уроков, непроверенные результаты и неизвестную длительность, если показываешь время. Отсутствие записи означает отсутствие данных, а не доказательство отсутствия занятий.

Обзор строится по запросу из единственного архива; отдельную ежегодную таблицу или второй журнал поддерживать не нужно. Настройку проекта и обсуждение навыка не включать в учебные достижения.
